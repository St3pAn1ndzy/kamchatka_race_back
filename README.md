# Авача — VK Mini App Backend

API мини-приложения ВКонтакте для фестиваля и гонки на собачьих упряжках «Авача»: участники, маршруты, координаты, протоколы, новости и программа

**FastAPI** · **PostgreSQL 16** · **Redis 7** · **Celery** · **SQLAdmin**

## Возможности

- Получение координат Iridium360 через Celery и отображение свежести данных: `fresh`, `delayed`, `stale`, `no_data`
- Официальные результаты по судейским отметкам `OfficialMark`, а не по времени GPS
- Карта участников, монитор трекеров, оперативный штаб и предупреждения SOS
- Ввод отметок, назначение оборудования, изменение статусов участников и журнал аудита
- Импорт KML/GPX: отдельная линия этапа либо маршруты с контрольными пунктами
- Новости, программа, FAQ, зрительские локации, подписки и очередь уведомлений
- Redis-кеш, метрики Prometheus и дашборд Grafana
- Фиксация согласия, анонимизация пользовательского профиля и маскирование чувствительных полей в логах

CSV-импорт не подключён к текущей админке, готового парсера судейских таблиц в этой версии нет

## Стек

Python 3.12 в Docker и CI, FastAPI, SQLAlchemy 2 async, Alembic, Pydantic 2, PostgreSQL 16, Redis 7, Celery и Celery Beat

Админка: SQLAdmin, Jinja2, Tabler UI и Яндекс Карты

Зависимости управляются Poetry, проверки выполняются Pytest, Node.js, Ruff, Schemathesis и Locust

В `pyproject.toml` разрешён Python `>=3.12,<4`, основной проверяемый CI интерпретатор — 3.12

## Локальный запуск

Все команды выполняются из корня клонированного проекта

Для Docker-варианта достаточно Git и работающего Docker Desktop либо Docker Engine с Compose, поддерживающим `--wait`

Python и Poetry на хосте нужны только для локального Uvicorn, скриптов демонстрации и проверок

<a id="docker-start"></a>

### Быстрый старт в Docker

**1. Подготовьте настройки**

```sh
test -f .env || cp .env.template .env
```

Оставьте `ENV=dev` для локальной работы

Если порт PostgreSQL 5432 занят, до запуска контейнера задайте в `.env` `POSTGRES_PORT=5433`

**2. Поднимите хранилища и примените миграции**

```sh
docker compose up -d --wait postgres redis
docker compose build api
docker compose run --rm --no-deps api alembic upgrade head
```

**3. При необходимости добавьте тестовые данные**

Для просмотра заполненной админки на локальной базе:

```sh
docker compose run --rm --no-deps api python -m scripts.seed_mock
```

Seed создаёт шесть этапов и учётную запись `admin / admin123`, подробнее — [о тестовых данных](#demo-data)

Для пустой базы пропустите этот шаг; демонстрационные реквизиты не подходят для публичного сервера

**4. Запустите API и проверьте ответ**

```sh
docker compose up -d api
curl --fail http://localhost:8000/health
```

Откройте [Swagger](http://localhost:8000/docs) или [админку](http://localhost:8000/admin-panel)

Если API ещё запускается, проверьте `docker compose logs --tail=100 api` и повторите запрос

> **Миграции:** контейнер не применяет их автоматически — после обновления кода с новыми миграциями повторите `alembic upgrade head`

<a id="python-start"></a>

### Альтернатива: локальный Python

<details>
<summary>Установка зависимостей и запуск Uvicorn через Poetry</summary>

Используйте Python 3.12 или новее и Poetry 2 с поддержкой `[project]` и `[dependency-groups]`

В Docker и CI используется Python 3.12

Если активно окружение другого проекта, сначала выйдите из него командой `deactivate`

Poetry может использовать уже активное окружение, поэтому проверяйте путь интерпретатора

Сначала создайте `.env` и проверьте подключения: `POSTGRES_HOST=localhost`, `REDIS_HOST=localhost`

Если порт 5432 занят, укажите `POSTGRES_PORT=5433` до создания контейнера PostgreSQL

```sh
poetry install --with dev
poetry env info --executable
poetry run python -c "import sys, sqlalchemy; print(sys.executable); print(sqlalchemy.__version__)"
test -f .env || cp .env.template .env
docker compose up -d --wait postgres redis
poetry run alembic upgrade head
docker compose stop api
poetry run uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

Compose публикует БД на выбранном порту, а внутри Docker используется адрес `postgres:5432`

То же разделение действует для Redis: опубликованный порт из `.env`, внутри Docker — `redis:6379`

API в Docker и локальный Uvicorn не могут одновременно занимать порт 8000

Чтобы наполнить обычную локальную базу, в другом терминале выполните `poetry run python -m scripts.seed_mock`

Закрыть Uvicorn можно сочетанием `Ctrl+C`

</details>

### Команды на каждый день

Команды в таблице относятся к API в Docker; они не управляют локальным Uvicorn

| Действие | Команда |
| --- | --- |
| Посмотреть состояние сервисов | `docker compose ps` |
| Открыть последние логи API | `docker compose logs --tail=100 -f api` |
| Открыть логи фоновых задач | `docker compose logs --tail=100 -f worker beat` |
| Остановить только API | `docker compose stop api` |
| Снова запустить API | `docker compose up -d api` |
| Остановить запущенные Compose-сервисы | `docker compose stop` |

После обновления зависимостей или миграций остановите API, пересоберите образ, примените миграции и запустите его заново:

```sh
docker compose stop api
docker compose build api
docker compose run --rm --no-deps api alembic upgrade head
docker compose up -d api
```

Если используете worker и Beat, пересоберите и перезапустите их тоже: `docker compose up --build -d worker beat`

### Адреса и фоновые задачи

| Адрес | Назначение |
| --- | --- |
| http://localhost:8000/docs | Swagger и актуальный контракт API |
| http://localhost:8000/admin-panel | Административная панель |
| http://localhost:8000/health | Проверка ответа API |
| http://localhost:8000/metrics | Метрики Prometheus |
| http://localhost:9090 | Prometheus в dev Compose |
| http://localhost:3001 | Grafana |

`/health` возвращает статус API и время, но не проверяет соединения с PostgreSQL, Redis или Iridium

Для варианта с API внутри Docker:

```sh
docker compose up --build -d worker beat prometheus grafana
```

Для локального Uvicorn запускайте фоновые задачи отдельно:

```sh
docker compose up --build -d worker beat
```

Prometheus зависит от Compose-сервиса `api`: его запуск обычной командой Compose также поднимет Docker API и займёт порт 8000

Показанная конфигурация мониторинга предназначена для Docker-варианта, для локального Uvicorn нужен отдельный адрес сбора метрик

В полном Docker-стеке worker обрабатывает задачи, Beat планирует опрос Iridium и обработку очереди уведомлений

Без этих процессов API доступен, но периодические задачи не выполняются

При `ENV=dev` и пустом `IRIDIUM_API_KEY` фабрика выбирает mock-клиент; с заданным ключом используется реальный клиент

Для реальной отправки ВК также нужны параметры сообщества и доступа из `.env.template`

<a id="troubleshooting"></a>

### Если запуск не получился

| Симптом | Что проверить |
| --- | --- |
| Docker сообщает о паузе | Возобновите Docker Desktop и проверьте `docker compose ps` |
| `No module named sqlalchemy` | Путь `poetry env info --executable`, активное окружение и `poetry install --with dev` |
| Порт 8000 занят | Остановите второй API: контейнер либо ранее запущенный Uvicorn |
| Таблица или столбец не найдены | Примените миграции в той же базе, к которой подключён API |
| Есть этапы, но нет линии маршрута | Проверьте выбранный профиль и наличие `StageRoutePoint`; профиль импорта изначально пустой |
| На карте ошибка ключа | Проверьте настройку Яндекс Карт в `app/templates/sqladmin/layout.html`; переменной ключа в `Settings` пока нет |
| Ошибка входа 429 | Подождите время `Retry-After` |
| Ошибка входа 503 | Проверьте Redis, общий счётчик входа недоступен |

## Тестовые данные и презентация

| Режим | Какие данные меняет | Когда выбирать |
| --- | --- | --- |
| `scripts.seed_mock` | Базу из текущих настроек `.env` и окружения | Обычная локальная разработка |
| `scripts.demo` | Только именованные базы `avacha_demo_overview` и `avacha_demo_import` | Обзор админки, движение с SOS и импорт KML/GPX |
| [Сервисные сценарии](#frontend-scenarios) | Всю базу, к которой подключён обслуживающий их API | Переключение экранов фронтенда на отдельном тестовом экземпляре |

### Обычный seed

```sh
poetry run python -m scripts.seed_mock
```

Стандартный набор содержит шесть этапов из `data/route-kamchatka.json`, 15 участников, маршруты, GPS и отметки

`--no-track` пропускает линии маршрута, GPS и судейские отметки, но создаёт КП

`--reset` очищает текущую базу, `--users` задаёт число mock-пользователей

По умолчанию seed разрешён в `ENV=dev`; `--force` снимает эту проверку и не является обычным шагом запуска

Созданные seed учётные данные `admin / admin123` предназначены только для локальной демонстрации

Сам вход в админку не ограничен `ENV=dev`, поэтому демонстрационный пароль нельзя оставлять на публичном сервере

<a id="admin-demo"></a>

### Две независимые демонстрации админки

**1. Подготовьте зависимости и хранилища**

Настройки `.env` должны указывать на локальные PostgreSQL и Redis, как в [варианте с Poetry](#python-start)

```sh
poetry install --with dev
docker compose up -d --wait postgres redis
docker compose stop api
```

**2. Подготовьте оба профиля**

| Профиль | Адрес | База | Redis DB | Начальное содержимое |
| --- | --- | --- | --- | --- |
| overview | http://127.0.0.1:8000 | avacha_demo_overview | 13 | Три этапа с маршрутами, GPS и отметками |
| route-import | http://localhost:8001 | avacha_demo_import | 14 | Шесть этапов без маршрутов, КП, GPS и отметок |

```sh
poetry run python -m scripts.demo prepare
```

Эта команда создаёт отсутствующие демобазы, применяет миграции и запускает соответствующие seed

Повторный запуск не очищает их автоматически; `prepare --reset` намеренно пересоздаёт оба набора

**3. Запустите серверы в двух терминалах**

```sh
# Терминал 1
poetry run python -m scripts.demo serve overview
```

```sh
# Терминал 2
poetry run python -m scripts.demo serve route-import
```

Перед этим остановите обычный контейнер API на 8000: `docker compose stop api`

Не запускайте весь Compose поверх этих серверов: обычный контейнер API использует настройки `.env` и другую базу

Сочетание `127.0.0.1:8000` и `localhost:8001` разделяет cookie административных сессий

Команды `scripts.demo` рассчитаны на локальный `ENV=dev` с локальными PostgreSQL и Redis

**4. Покажите движение и SOS**

Откройте карту участников в обзорной админке на `127.0.0.1:8000`, затем в третьем терминале запустите:

```sh
poetry run python -m scripts.demo move --device-id 1 --steps 24 --interval 5 --sos-at 6
```

`device-id` — ID устройства, не IMEI и не номер участника

Скрипт движется от начала до конца линии, включает SOS с заданного шага и при штатном завершении удаляет свои точки

Сценарий ускоренный и не обращается к реальному Iridium; принудительное завершение процесса не гарантирует очистку

<a id="frontend-scenarios"></a>

### Сервисные сценарии веб-приложения

> **Очистка данных:** переключение сценария пересоздаёт текущую базу, включая пользователей, администраторов и аудит — используйте отдельный одноразовый экземпляр

<details>
<summary>Маршруты для фронтенда и ограничения текущей реализации</summary>

Текущий API второго разработчика: `/api/v1/dev/scenarios`

| Метод и путь | Действие |
| --- | --- |
| `GET /api/v1/dev/scenarios/` | Список имён сценариев |
| `POST /api/v1/dev/scenarios/upcoming` | Шесть запланированных этапов с маршрутами и КП, зарегистрированные участники, без трекеров, GPS и отметок |
| `POST /api/v1/dev/scenarios/live` | Этап 1 завершён, этап 2 активен, у десяти участников GPS-треки, есть подписки и отметки |
| `POST /api/v1/dev/scenarios/finished` | Все этапы и участники завершены, финишные отметки и анонс следующей гонки |
| `POST /api/v1/dev/scenarios/move/{device_id}?steps=15` | Фоновое движение устройства от 65% до конца линии с шагом раз в три секунды |

Каждый POST переключения сценария выполняет `TRUNCATE … CASCADE` текущей базы, пересоздавая в том числе пользователей, администраторов и аудит

Код проверяет только `ENV=dev`: отдельной аутентификации, привязки к демобазе и изоляции Redis у этого API пока нет

При другом `ENV` методы возвращают 403, но остаются в OpenAPI

Такой экземпляр нельзя подключать к рабочей базе или выставлять для общего доступа без дополнительного ограничения доступа

Для него нужна отдельная одноразовая база; переключение может потребовать повторного входа в админку

После POST фронтенд перечитывает данные и обновляет свой экран

Известные ограничения текущих сценариев:

- В `finished` и в результатах первого этапа `live` нет парных отметок старта и финиша, поэтому итоговое время и места остаются пустыми
- HTTP-движение оставляет демоточки на финише, повторный запуск для того же устройства блокируется
- `steps` не проверяется на допустимый диапазон, значение 1 приводит к ошибке вычисления
- Ответ `movement_started` подтверждает постановку фоновой задачи, а не успешное завершение движения
- HTTP-движение не включает SOS и не создаёт официальную отметку финиша

Не переключайте сценарии во время HTTP-движения: оно выполняется в фоне, отдельного маршрута остановки пока нет

Это отдельный режим, его нельзя смешивать с `scripts.demo move`, который очищает свои точки

</details>

## Импорт KML и GPX

В админке доступны две формы на странице «Гонка и маршрут»

Предпросмотр не меняет БД, сохранение требует административной сессии, подтверждения и CSRF-проверки

| Форма | Поддержка | Ограничения |
| --- | --- | --- |
| «Импорт маршрута с КП» | Один или несколько этапов с явным сопоставлением линий, направления и типов КП | До 8 МиБ, 32 этапов, 2–20000 точек в линии, 100000 точек всего, 100 КП на этап |
| «Замена только линии маршрута» | Одна линия KML `LineString` либо один GPX `rte` / `trk` с одним `trkseg` | До 2 МиБ, 2–2000 точек |

Полный KML ожидает одну линию и точки КП в папке этапа

В GPX каждый корневой `trk` или `rte` задаёт этап; глобальные `wpt` допустимы только при одном этапе

KMZ, несколько сегментов трека и неподдерживаемые XML-расширения не принимаются

Высоты КП из полного импорта сохраняются при наличии в файле

Для всех линий нужно выбрать разные существующие этапы одного сезона, проверить направление и задать типы КП

Все выбранные этапы сохраняются одной транзакцией, ошибка одного не должна оставлять частично заменённую трассу

На активном этапе или при наличии GPS/отметок можно переносить существующие КП, сохранив названия, типы и количество

Если в пакете есть такой этап, это ограничение действует на КП всех выбранных этапов

История отметок и GPS сохраняется, длина и километраж КП пересчитываются, кеш обновляется

Завершённые этапы менять нельзя

Замена только линии не переносит координаты КП; если КП оказались вне новой линии, используйте импорт с КП

Подробнее о действиях оператора — в [руководстве сотрудников](docs/staff-guide.md)

## Проверки

### Pytest и JavaScript

Интеграционные тесты требуют отдельной PostgreSQL-базы с именем, оканчивающимся на `_test`, и Redis DB 15

Для стандартных реквизитов создайте её один раз:

```sh
docker compose exec postgres createdb -U avacha avacha_test
```

Если база уже существует, повторять создание не нужно; при других реквизитах замените имя роли

Настройки `ENV=test`, `POSTGRES_DB=avacha_test`, `REDIS_DB=15` задаются через `pyproject.toml`

Тесты создают и удаляют схему этой базы, кеш Redis DB 15 очищается до и после тестов

Не запускайте несколько прогонов одновременно с одними тестовыми ресурсами

```sh
poetry run pytest -q
node --test tests/js/*.test.cjs
poetry run ruff check app/ tests/
poetry run ruff format --check app/ tests/
poetry run python -m scripts.export_openapi
```

CI запускает Python-проверки на 3.12, PostgreSQL 16 и Redis 7, JavaScript-проверки — на Node.js 22

Проверки PR включают Ruff, Pytest, JavaScript и генерацию OpenAPI

### Schemathesis

Запускайте на отдельном тестовом экземпляре API

Пример проверки GET-маршрутов без намеренного запуска изменяющих операций:

```sh
poetry run schemathesis run http://localhost:8000/openapi.json --include-method GET --checks all
```

Полный прогон с POST/PATCH/DELETE может изменять данные, в том числе вызвать dev-сценарии с очисткой базы

### Locust и сохранённые измерения

```sh
poetry run locust -f loadtests/locustfile.py --host=http://localhost:8000
```

Сценарий использует участников с ID 1–15 и этап с ID 1; подготовьте подходящий набор данных

Снимок [предыдущего нагрузочного прогона](docs/load-test-prod-stats.png) фиксирует 1000 виртуальных пользователей, 200,8 RPS, медиану 3 мс, p95 7 мс и 8 ошибок из 70376 запросов — около 0,011%

<a id="monitoring"></a>

## Мониторинг

API отдаёт `/metrics`, Prometheus обращается к `api:8000` каждые 10 секунд

При API, запущенном на хосте вместо Compose-сервиса `api`, этот адрес мониторинга нужно менять отдельно

HTTP-метрики и бизнес-счётчики описаны в `app/metrics.py`, дашборд — в `monitoring/dashboards/avacha.json`

В dev Grafana доступна на 3001 с начальными локальными реквизитами `admin / admin`

В dev Compose источник данных автоматически не подключается: добавьте Prometheus с адресом `http://prometheus:9090` в настройках Grafana и выберите его для панелей при необходимости

В production Compose смонтированы настройки и источника данных, и дашбордов

Prometheus проверяет HTTP-метрики, а не наличие реального спутникового соединения или доставку каждого уведомления

<a id="production"></a>

## Production Compose

До запуска настройте `.env`: уникальные `SECRET_KEY`, `ADMIN_PANEL_SESSION_SECRET`, пароли PostgreSQL и Grafana, доступы ВК и Iridium, CORS и доверенный reverse proxy

В prod без ключа Iridium фабрика реального клиента не работает

Не создавайте рабочие учётные записи через mock-seed с известными реквизитами

```sh
docker compose -f docker-compose.prod.yml build api worker beat
docker compose -f docker-compose.prod.yml up -d --wait postgres redis
docker compose -f docker-compose.prod.yml run --rm --no-deps api alembic upgrade head
docker compose -f docker-compose.prod.yml up -d api worker beat prometheus grafana
```

Конфигурация запускает четыре процесса Uvicorn и worker Celery с concurrency 4, принудительно задаёт `ENV=prod` и `DEBUG=false`

PostgreSQL, Redis и Prometheus не публикуют порты наружу; Grafana опубликована на `127.0.0.1:3001`, API — на 8000

Для удалённого доступа к Grafana можно использовать SSH-туннель:

```sh
ssh -L 3001:localhost:3001 user@server
```

TLS, домен, резервное копирование и создание рабочих администраторов этот Compose автоматически не настраивает

Redis использует `noeviction`: при заполнении памяти новые записи отклоняются, объём памяти нужно контролировать

`FORWARDED_ALLOW_IPS` должен содержать адрес доверенного прокси, а не произвольных клиентов

<a id="settings"></a>

## Настройки

Полный список полей — в `app/config.py`, пример локальных значений — в `.env.template`

Пустые параметры ВК не мешают открыть локальный API, но не обеспечивают настоящую VK-авторизацию или отправку сообщений

| Настройка | Назначение |
| --- | --- |
| `ENV`, `DEBUG` | Окружение, режим отладки и secure-cookie SQLAdmin |
| `POSTGRES_*`, `REDIS_*` | Подключения и номер базы кеша |
| `CELERY_BROKER_DB`, `CELERY_RESULT_DB` | Отдельные Redis DB для брокера и результатов Celery |
| `SECRET_KEY`, `ADMIN_PANEL_SESSION_SECRET` | Подпись JWT и административной cookie-сессии |
| `VK_APP_ID`, `VK_SECURE_KEY`, `VK_GROUP_ID`, `VK_SERVICE_TOKEN` | Доступ к ВК |
| `IRIDIUM_*` | Доступ к Iridium и параметры запросов |
| `TRACKING_POLL_INTERVAL_SECONDS` | Интервал опроса, по умолчанию 900 секунд |
| `TRACKING_STALE_MISSED_INTERVALS` | Число пропущенных интервалов до устаревания данных |
| `CACHE_TTL_*` | Время жизни кешированных ответов |
| `ADMIN_LOGIN_MAX_ATTEMPTS`, `ADMIN_LOGIN_WINDOW_SECONDS` | По умолчанию 10 попыток входа за 60 секунд с одного IP |
| `CORS_ORIGINS`, `CORS_ORIGIN_REGEX` | Разрешённые источники запросов веб-приложения |
| `FORWARDED_ALLOW_IPS` | Доверенные прокси Uvicorn в production Compose |
| `GRAFANA_ADMIN_*`, `GRAFANA_ROOT_URL` | Параметры Grafana в production Compose |

Лимит входа общий для SQLAdmin и административного API, включает успешные попытки и действует между процессами

При превышении возвращается 429 с `Retry-After`, при недоступном Redis — 503

Остальные маршруты этим лимитом не ограничиваются
